# Accessibility & Website Test Report — 2026-08-25

**Target:** http://localhost:3000 (`next dev`, Next.js 16.3.2 Turbopack) · commit `2b416e8`
**Standard:** WCAG 2.2 Level AA (Level A as hard floor)
**Tooling:** Playwright 1.57 (chromium 145, firefox 148) · axe-core 4.11 via `@axe-core/playwright`
**Scope:** `/` and `/polityka-prywatnosci` · light + dark themes · 320×568, 375×812, 768×1024, 1280×800, 1920×1080 · `prefers-reduced-motion` both states · JavaScript enabled and disabled
**Specs:** `tests/specs/` — reproduce with `npx playwright test --config tests/playwright.config.ts`

### Test conditions worth knowing

The consent banner **only renders when `NEXT_PUBLIC_GA_ID` is set**. There is no
`.env` in the working tree, so on a default local run the banner never appears
and neither axe nor the keyboard sweep sees it. Everything in this report that
concerns the banner was re-run against a server started as:

```bash
NEXT_PUBLIC_GA_ID=G-TEST1234567 npx next dev
```

with all non-localhost requests aborted in the browser, so nothing ever reached
Google. **If production sets a GA id, finding C-1 is live in production.**

### A note on the working tree

Twenty-seven files under `components/` plus `README.md` and `.gitignore` were
modified on disk **by something other than this test run** while it was in
progress (the changes look like a formatter pass — quote style, trailing commas).
Nothing under `app/` changed, so every `app/globals.css` reference below is exact.
All findings were re-verified against the post-change files and every one still
holds; a few line numbers in `components/consent/ConsentBanner.tsx` shifted by
one or two and have been corrected here. This run touched only `tests/`,
`package.json` and `package-lock.json` (the Playwright/axe dev dependencies).

### Not covered

- **WebKit / Safari.** The browser downloaded but will not launch on this host:
  `Host system is missing dependencies to run browsers` (`sudo npx playwright install-deps`,
  which needs root). The config declares a `webkit` project behind `WEBKIT=1`; it was never run.
- **A real screen-reader session.** Role/name/reading-order checks were done by
  inspecting the accessibility tree via Playwright's `ariaSnapshot()`, not by
  running NVDA, JAWS or VoiceOver.
- **End-to-end contact-form submission.** The form posts to Netlify Forms; no
  live enquiry was sent. Only client-side validation behaviour was exercised.
- **axe at 768×1024 and 1920×1080.** The axe sweep ran at 320, 375 and 1280 on
  both routes and both themes (12 configurations) plus 2 more with the banner
  visible. The other two viewports were covered by the reflow/overflow specs but
  not by axe.
- **Performance, CLS and Lighthouse metrics.** Not measured.

## Summary

| Severity | Count |
|---|---:|
| Critical | 1 |
| Serious  | 6 |
| Moderate | 8 |
| Minor    | 4 |
| **Total** | **19** |

The site is in better shape than the raw count suggests. The reduced-motion
architecture is deliberate and mostly correct, no content is lost without
JavaScript, the consent gating is genuinely compliant, form fields are all
properly labelled, and there are no console errors, broken links or hydration
mismatches. The failures cluster into two root causes and one interaction bug.

**Fix first: the consent banner hides the contact form's submit button from
keyboard users (C-1).** While the banner is on screen, five controls — including
the message field and *Wyślij zapytanie* — are completely covered when focused.
A keyboard visitor cannot see what they are about to activate on the one
conversion path the site has. Everything else is a token change or a CSS gate.

Two root causes account for eight of the nineteen findings: the light-theme
`--accent` value (S-1, S-2, S-5, and part of M-1) and the ungated marquee
animation (S-3). Fixing those two lines removes most of the report.

## Findings

### [CRITICAL] C-1 — Consent banner hides focused controls, including the form's submit button

- **WCAG:** 2.4.11 Focus Not Obscured (Minimum) — Level AA (new in WCAG 2.2)
- **Where:** [components/consent/ConsentBanner.tsx:61](components/consent/ConsentBanner.tsx#L61) — `fixed inset-x-0 bottom-0 z-90` · `/` · 1280×800 · both themes · chromium + firefox
- **Condition:** only when `NEXT_PUBLIC_GA_ID` is set
- **Evidence:** tabbing through the page with the banner up, `document.elementFromPoint()` at the focused element's centre returns a node inside `[role="dialog"]` for five controls:

  | Focused control | Covered by |
  |---|---|
  | `TEXTAREA[name=wiadomosc]` | consent dialog body |
  | `BUTTON` *Wyślij zapytanie* | consent *Odrzuć* button |
  | `A` *polityką prywatności* | consent panel |
  | `A` *Polityka prywatności · RODO* | consent panel wrapper |
  | `BUTTON` *Ustawienia prywatności* | consent *Dostosuj ustawienia* |

  Screenshots: `tests/screenshots/2026-08-25/focus-behind-banner.png`, `contact-light.png`
- **Impact:** a sighted keyboard user filling in the contact form cannot see the field or button that has focus. They are asked to submit a form blind, or to dismiss a consent dialog they cannot reach without first tabbing past the entire page (see S-4). This is the site's only conversion path.
- **Reproduce:** `NEXT_PUBLIC_GA_ID=G-TEST1234567 npx next dev`, then `npx playwright test --config tests/playwright.config.ts specs/focus-obscured.spec.ts`
- **Recommendation:** while the banner is displayed, reserve the space it occupies — e.g. add bottom padding to `<body>` equal to the banner height, or use `scroll-padding-bottom` plus a `scroll-margin` on focusable elements. Moving focus into the dialog on appearance (S-4) also resolves most of this, because the visitor dismisses the banner before reaching the page.

### [SERIOUS] S-1 — Light-theme `--accent` fails text contrast wherever it is used

- **WCAG:** 1.4.3 Contrast (Minimum) — Level AA
- **Where:** [app/globals.css:49](app/globals.css#L49) — `--accent: #b8935a`
- **Evidence:** measured ratios against the light-theme backgrounds:

  | Foreground | Background | Ratio | Required |
  |---|---|---:|---:|
  | `#b8935a` | `--bg` `#f4f1ea` | **2.53:1** | 4.5:1 (small) / 3:1 (large) |
  | `#b8935a` | `--bg-alt` `#e8e4dc` | **2.25:1** | 4.5:1 / 3:1 |

  axe instances (light theme, deduplicated by root cause):
  - `.pricing-line` *✦ Bez pośredników* — 2.25:1 at 11.2px — [components/Pricing.tsx](components/Pricing.tsx)
  - `<span class="text-(--accent)"> zł</span>` — 2.25:1 at 115px — [components/Pricing.tsx](components/Pricing.tsx)
  - `<span class="italic text-(--accent)">wprost.</span>` — 2.52:1 at 102px — [components/Contact.tsx](components/Contact.tsx)
  - `<a class="text-(--accent)">dommeszna@proton.me</a>` — 2.28:1 at 18px — [app/polityka-prywatnosci/page.tsx](app/polityka-prywatnosci/page.tsx)
  - `<span class="italic" style="color:var(--accent)">prywatności</span>` — 2.52:1 — privacy page `<h1>`
  - `✦ Prywatność` — 2.52:1 at 11.2px — [components/consent/ConsentBanner.tsx:73](components/consent/ConsentBanner.tsx#L73)

  Dark theme is fine: `--accent: #d4a76a` on `#0e0e0c` = **8.77:1**.
- **Impact:** the price, the contact-section headline, the privacy-policy heading and the only published email address are all below threshold for low-vision users in the default (light) theme.
- **Reproduce:** `npx playwright test --config tests/playwright.config.ts specs/axe.spec.ts -g "light"`
- **Recommendation:** darken the light-theme token only. `#795e34` gives 5.37:1 on `--bg` and 4.78:1 on `--bg-alt`, passing for body text at any size; `#806437` (4.90:1 / 4.36:1) passes on `--bg` but is marginal on `--bg-alt`. If the warm-gold tone must be preserved at display sizes, introduce a second token (e.g. `--accent-strong`) for text and keep `#b8935a` for large decorative marks only — but note the `✦` labels are 11.2px, so they need the text-grade value.

### [SERIOUS] S-2 — Focus indicator itself is below the non-text contrast threshold in light theme

- **WCAG:** 1.4.11 Non-text Contrast — Level AA
- **Where:** [app/globals.css:176-179](app/globals.css#L176-L179) — `:focus-visible { outline: 1px solid var(--accent); outline-offset: 2px; }`
- **Evidence:** the indicator inherits the same token as S-1 — **2.53:1** against `--bg` and **2.25:1** against `--bg-alt`, where 1.4.11 requires **3:1**. Confirmed as the computed outline colour on every one of the 12 tab stops recorded (`rgb(184, 147, 90)`). Screenshot: `tests/screenshots/2026-08-25/focus-indicator-light.png`. Dark theme passes at 7.91–8.77:1.
- **Impact:** every focusable element on the site in the default theme. Keyboard users lose track of position; combined with C-1 the form becomes effectively unusable without a mouse.
- **Reproduce:** `npx playwright test --config tests/playwright.config.ts specs/keyboard.spec.ts -g "tab order"`
- **Recommendation:** fixing S-1 fixes this automatically. Additionally consider a 2px outline — 1px at `outline-offset: 2px` is easy to lose against textured hero imagery, and WCAG 2.2's 2.4.13 (AAA) expects a 2px-equivalent area.

### [SERIOUS] S-3 — Marquee animates forever, ignores `prefers-reduced-motion`, and has no pause control

- **WCAG:** 2.2.2 Pause, Stop, Hide — **Level A** (also 2.3.3 Animation from Interactions, AAA)
- **Where:** [app/globals.css:141-143](app/globals.css#L141-L143) — `.marquee-track { animation: marquee 40s linear infinite; }` · [components/Marquee.tsx](components/Marquee.tsx)
- **Evidence:** with `prefers-reduced-motion: reduce` emulated, the computed style is still `animation-name: marquee`, `animation-duration: 40s`, `animation-iteration-count: infinite`. A search for any pause/stop control returns **0**. The GSAP work is correctly gated by `useSectionAnim`'s `MOTION` matchMedia — but this is a plain CSS keyframe animation, so the JS gate never touches it.
- **Impact:** continuous horizontal motion that a visitor cannot stop. For users with vestibular disorders this can cause nausea and headache; for users with attention-related disabilities it makes the adjacent content hard to read. 2.2.2 is Level A — the floor.
- **Reproduce:** `npx playwright test --config tests/playwright.config.ts specs/motion.spec.ts`
- **Recommendation:** add the CSS gate the JS already has:
  ```css
  @media (prefers-reduced-motion: reduce) {
    .marquee-track { animation: none; }
  }
  ```
  `aria-hidden="true"` on the section ([components/Marquee.tsx:20](components/Marquee.tsx#L20)) correctly keeps it out of the accessibility tree, but 2.2.2 is about visible motion, so the hiding does not satisfy it. A visible pause toggle would also satisfy the SC for users who have not set the OS preference.

### [SERIOUS] S-4 — Consent dialog is the last thing in the tab order and never receives focus on appearance

- **WCAG:** 2.4.3 Focus Order — Level A (contributes to C-1)
- **Where:** [components/consent/ConsentBanner.tsx:60-74](components/consent/ConsentBanner.tsx#L60-L74)
- **Evidence:** recorded tab sequence from page load with the banner visible — the first banner control is reached at **stop 15**, after the entire page including the footer:

  ```
   1 A      Dom w Mesznej / Bez pośredników
   2 A      Umów oglądanie
   3 BUTTON Przełącz motyw
   4-8      contact form inputs + textarea
   9 BUTTON Wyślij zapytanie
  10 A      polityką prywatności
  11 A      dommeszna@proton.me
  12 A      Polityka prywatności · RODO
  13 BUTTON Ustawienia prywatności
  14 (dev-tools portal)
  15 BUTTON Odrzuć          ← first consent control
  ```

  `document.activeElement` on load is `BODY` — focus is never moved into the dialog. The `panel.current?.focus()` call at [ConsentBanner.tsx:46](components/consent/ConsentBanner.tsx#L46) runs only inside the `showPrefs` effect, i.e. on the reopen-from-footer path, not on first appearance.
- **Impact:** a keyboard or screen-reader visitor meets a `role="dialog"` that is visually first and programmatically last. To accept or reject they must traverse the whole page, and along the way they hit the controls that C-1 has hidden behind that very dialog.
- **Reproduce:** `npx playwright test --config tests/playwright.config.ts specs/consent-semantics.spec.ts`
- **Recommendation:** move focus to the panel when the banner first appears, exactly as the reopen path already does. The reopen path is correct — focus enters the panel, `Escape` closes it — so this is a matter of extending existing behaviour to the initial render.

### [SERIOUS] S-5 — Email links on the privacy page are distinguished from body text by colour alone

- **WCAG:** 1.4.1 Use of Colour — Level A
- **Where:** [app/polityka-prywatnosci/page.tsx](app/polityka-prywatnosci/page.tsx) — `<a class="text-(--accent) hover:underline">dommeszna@proton.me</a>`

### [MODERATE] M-1 — `opacity-50` on muted text drops it below 4.5:1

- **WCAG:** 1.4.3 Contrast (Minimum) — Level AA
- **Where:** footer `<p class="opacity-50 text-sm">© 2026 Wszelkie prawa zastrzeżone</p>` ([components/Footer.tsx](components/Footer.tsx)); `<span class="label-mono opacity-50 text-xs">01</span>` and siblings on the privacy page

### [MODERATE] M-3 — Header control is clipped at a 320 px viewport

- **WCAG:** 1.4.10 Reflow — Level AA
- **Where:** [components/Header.tsx](components/Header.tsx) — theme-toggle `button.w-11.h-11`
- **Evidence:** at 320×568 the button's bounding box runs `left: 283 → right: 327` against a 320 px viewport — **7 px cut off**. `document.documentElement.scrollWidth` is 326 vs `clientWidth` 320; because `body { overflow-x: hidden }` ([app/globals.css:82](app/globals.css#L82)) the overflow is clipped rather than scrollable, so the content is unreachable rather than merely off-screen. Visually confirmed: `tests/screenshots/2026-08-25/header-320.png` shows the moon icon sliced by the right edge. Reproduced on chromium and firefox. At 375 px the header fits (measured overflow there comes only from the marquee track, which is inside an `overflow-hidden` container and is expected).
- **Impact:** the theme toggle is partly unusable on the narrowest supported viewport — 320 px is also what a 400% zoom on a 1280 px screen produces.
- **Recommendation:** reduce the header's horizontal padding or the `gap-3` below the `sm` breakpoint so the row fits within 320 px.

### [MODERATE] M-4 — Home page overflows horizontally under the WCAG text-spacing override

- **WCAG:** 1.4.12 Text Spacing — Level AA
- **Where:** `/` at 375×812
- **Evidence:** applying the SC 1.4.12 override (line-height 1.5, letter-spacing 0.12em, word-spacing 0.16em, paragraph spacing 2em) takes `scrollWidth` from 375 to **430 px** — 55 px of overflow, clipped by `overflow-x: hidden`. The privacy page is unaffected (375 → 375). Screenshot: `tests/screenshots/2026-08-25/text-spacing-home.png`
- **Impact:** users who apply a spacing stylesheet for dyslexia or low vision lose content at the right edge on the home page.
- **Recommendation:** the fixed-width and `clamp()`-sized display headings are the likely cause; allow them to wrap (`overflow-wrap: break-word`, `hyphens: auto`) and avoid `white-space: nowrap` on wide text at small breakpoints.

### [MODERATE] M-5 — No live region announces contact-form submission status

- **WCAG:** 4.1.3 Status Messages — Level AA; 3.3.1 Error Identification — Level A (partial)
- **Where:** [components/Contact.tsx](components/Contact.tsx)
- **Evidence:** the document contains **zero** `[aria-live]`, `[role="alert"]` or `[role="status"]` elements. Fields carry no `aria-invalid` or `aria-describedby`. Submitting the form empty is blocked by native constraint validation only — `imie` and `email` report `validity.valid: false` with the browser's own bubble, and **no POST is issued** (verified: `posts-made: []`, so no live Netlify request was made during testing).
- **Impact:** native validation bubbles are announced by most screen readers, so 3.3.1 is partially met — but the *outcome* of a successful or failed submission has nothing to announce it. A screen-reader user cannot tell whether their enquiry was sent.
- **Recommendation:** render success and failure into a `role="status"` region, and pair `aria-invalid` + `aria-describedby` with persistent inline error text rather than relying solely on native bubbles (which vanish on blur and appear in the browser's UI language, not the page's — observed as English *"Please fill out this field"* on this Polish page).

### [MODERATE] M-6 — `scroll-behavior: smooth` is not gated by `prefers-reduced-motion`

- **WCAG:** 2.3.3 Animation from Interactions — Level AAA (reported as an AA-adjacent recommendation)
- **Where:** [app/globals.css:71](app/globals.css#L71)
- **Evidence:** with `prefers-reduced-motion: reduce` emulated, `getComputedStyle(document.documentElement).scrollBehavior` is still `smooth`. Every in-page anchor (`/#kontakt`) and every keyboard focus move to an off-screen element therefore animates the whole viewport.

### [MODERATE] M-7 — Statement heading sits at 1.28–1.39:1 until the visitor scrolls through it

- **WCAG:** 1.4.3 Contrast (Minimum) — Level AA (conditional)
- **Where:** [components/Statement.tsx:13-29](components/Statement.tsx#L13-L29) — `gsap.fromTo('.stmt-word', { opacity: 0.12 }, { opacity: 1, scrub: 1 })`
- **Evidence:** axe measured every word of this `<h2>` at **1.39:1** (dark, `#343431` on `#1a1a18`) and **1.28:1** (light, `#cecac3` on `#e8e4dc`) — 29–33 nodes per configuration, the bulk of the raw axe count. Verified this is transient: scrolling through the section takes every word to `opacity: 1` (measured min 1, max 1), and under `prefers-reduced-motion: reduce` the words are `opacity: 1` from the start (measured `["1"]`).
- **Impact:** genuinely mitigated, but not eliminated — the readability of a heading is tied to scroll position, so a user who lands mid-section via an anchor, or who scrolls in coarse jumps, can be left reading near-invisible text. Reduced-motion users are unaffected.
- **Recommendation:** raise the starting opacity to a value that clears 3:1 for large text (roughly 0.45 on `--bg-alt`) so the effect still reads as a reveal while every intermediate state stays legible.

### [MODERATE] M-8 — No skip link; sections carry no accessible names

- **WCAG:** 2.4.1 Bypass Blocks — Level A (arguably met via headings); 1.3.1 Info and Relationships — Level A
- **Where:** [app/layout.tsx](app/layout.tsx), [app/page.tsx](app/page.tsx)
- **Evidence:** the first tab stop is the logo link, not a skip link — no element matching `#main`/`skip`/`przejdź` exists. There is **no `<nav>` element on either route** (the header holds only a logo and one CTA — this is a deliberate single-page design, not a missing menu). 12 `<section>` elements on `/` and 12 on the privacy page have neither `aria-label` nor `aria-labelledby`. `<main>`, `<header>` and `<footer>` are all present and correct, and every section does carry an `<h2>`.
- **Impact:** because each section has a heading, screen-reader users have a working bypass mechanism (technique H69), so 2.4.1 is arguably satisfied. The practical loss is that sections do not appear as navigable landmarks, and there is no bypass at all for sighted keyboard users on a 24,000 px page.
- **Recommendation:** add a visually-hidden-until-focused skip link to `#main`, and `aria-labelledby` on each `<section>` pointing at its own `<h2>`. Both are small additions that turn the existing heading structure into a landmark structure.

## Passed checks

Verified as conforming, not assumed:

**Consent and privacy**
- No third-party request of any kind before consent — network log empty (`external-before-consent: []`).
- `https://www.googletagmanager.com/gtag/js` loads **only** after *Akceptuj*; the *Odrzuć* path loads nothing.
- Consent choice persists across reload; the banner does not reappear.
- The banner is a proper `role="dialog"` with `aria-labelledby` (*"Zgoda na analitykę"*) and `aria-describedby`, and `aria-modal="false"` correctly reflects that it is non-blocking.
- *Odrzuć* and *Akceptuj* are visually equal — identical 345 × 43 px boxes, same border, same 18 px type. No dark pattern.
- Reopening from the footer moves focus into the panel and `Escape` closes it.

**Motion**
